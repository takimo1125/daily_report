## わかったこと
### TypeScript / Node.js
TypeScriptはAltJS（Alternative JavaScript）と呼ばれるJavaScriptの代替言語の1つです。
JavaScriptに型定義の仕組みを追加した言語であり、開発時にエラーを発見しやすくなります。
TypeScriptはそのままでは実行できず、JavaScriptへ変換（トランスパイル）して実行するのが基本です。
Node.jsはJavaScriptの実行環境の一種です。
本来コンピューターはJavaScriptやTypeScriptを直接実行できません。Node.jsやブラウザがJavaScriptを解釈して実行します。
NPM（Node Package Manager）はNode.jsのパッケージマネージャーです。
ライブラリやツールのインストール、依存関係の管理を行います。

### 開発モードと本番モード
#### 開発モード
- ソースコードを書き換えると即時自動反映される
- ホットリロードやライブリロードが有効になることが多い
- デバッグのため細かいログを出力する
- エラーメッセージを詳細に表示する

#### 本番モード
- ソースコードを書き換えても自動では反映されない
- 開発用機能を削減して高速に動作する
- セキュリティや性能を重視した設定になる

アプリケーションによっては開発モードと本番モードで実行手順が異なる場合があります。

### テスト
ソフトウェア開発では品質を保証するために様々なテストを実施します。

#### 単体テスト（Unit Test）
プログラムの関数やクラス単位で実施するテストです。

#### APIテスト
Web APIの入出力を確認するテストです。

#### E2Eテスト（End to End Test）
ブラウザを自動操作し、ユーザー操作を再現するテストです。
画面操作からAPI連携までシステム全体を確認できます。

### ビルド
ビルドとはソースコードから本番環境で実行可能な成果物を作成する工程です。
ビルドには以下のような処理が含まれます。

- コンパイル
- トランスパイル
- バンドル
- パッケージング
- 最適化

#### コンパイル
人間が書いたコードをコンピューターが扱いやすい形式へ変換します。

#### バンドル
複数のJavaScriptファイルを1つまたは少数のファイルへまとめる処理です。

#### パッケージング
配布可能な形式へまとめる処理です。

#### コンテナイメージのビルド
Dockerなどのコンテナイメージを作成することもビルドと呼びます。

ビルドのないアプリケーションも存在します。
例
- Ruby
- PHP
- Python

ただし近年はこれらもデプロイ用のパッケージ作成やコンテナ化を行うことがあります。

### フロントエンド
ブラウザは以下を読み込みます。

- HTML
- CSS
- JavaScript

近年はReactやVueが利用されることが多いです。
ReactではJSX、VueではSingle File Componentという独自形式を利用します。
ブラウザはJSXやVueファイルを直接実行できないためJavaScriptへ変換する必要があります。
このためフロントエンド開発ではNode.jsベースのビルドツールが利用されます。
代表例
- Vite
- Webpack
- Parcel

### Git / GitHub
Gitは分散型バージョン管理システムです。
ソースコードの変更履歴を管理できます。
GitHubはGitリポジトリをホスティングするサービスです。
チーム開発やレビュー機能も提供しています。

#### Git Status
Gitの管理状態を確認します。
`git status`

#### Git Add
コミット対象のファイルをステージングします。
`git add .`

#### Git Commit
変更内容のスナップショットを作成します。
`git commit -m "message"`

#### Git Push
ローカルのコミットをGitHubへアップロードします。
`git push`

### GitHub Actions
GitHub上でCI/CDを実現するための自動化機能です。
リポジトリのイベントをトリガーとしてワークフローを実行できます。

#### CI（Continuous Integration）
ソースコードのPushやPull Requestを契機に以下を実施します。

- ビルド
- テスト
- 静的解析
- フォーマットチェック

#### GitHub Actionsの構成
- **Workflow**: 処理全体の定義
- **on**: トリガー定義
- **Job**: 実行単位
- **Step**: Job内の個々の処理
- **Action**: 再利用可能な処理部品

#### GitHub Actionsが表示されない場合
確認事項
- `.github/workflows` にYAMLファイルが配置されているか
- YAMLのインデントが正しいか
- GitHub Actionsが有効か
- エラーログが出ていないか

#### ワークフローの定期実行
cron設定により定期実行できます。
用途例
- 長時間かかるテスト
- 依存ライブラリ確認
- 脆弱性チェック
- 定期バックアップ

### StepCI
StepCIはWeb API向けの自動テストツールです。
特徴
- YAML形式で記述可能
- HTTPレスポンス内容まで検証可能
- CLI実行可能
- CIへ組み込みやすい

#### ローカルインストール

`npm install package-name`
基本的にはローカルインストールを推奨します。

#### Dependencies
本番環境でも利用するライブラリ

#### DevDependencies

#### npx
ローカルインストールしたパッケージを実行するコマンド
`npx eslint .`

#### npm script
package.jsonに定義したコマンドを実行できます。
`npm run build`
`npm run test`

### AWS
AWS（Amazon Web Services）はAmazonが提供するクラウドサービス群です。

#### EC2
仮想サーバーサービス
AMI（Amazon Machine Image）をもとにインスタンスを起動します。

#### Linuxコマンド
プロセス確認
`ps aux`

ポート確認
`sudo ss -antp`

プロセスツリー確認
`pstree -p`

#### systemd
Linuxでサービス管理を行う仕組みです。
サービスの自動起動や監視を行います。

ログ確認
`journalctl -u backend`

サービス起動
`sudo systemctl start backend`

設定反映
`sudo systemctl daemon-reload`

状態確認
`systemctl status backend`

### デプロイとリリース
- **デプロイ**: ビルド成果物をサーバーへ配置すること
- **リリース**: ユーザーへ公開すること

#### CD（Continuous Delivery / Continuous Deployment）
CIに加えてデプロイまで自動化する考え方です。

#### CI/CD
CIとCDを組み合わせた開発手法です。

#### S3
AWSのオブジェクトストレージサービスです。
データはバケットという単位で管理します。
用途
- 静的サイト公開
- ファイル保存
- バックアップ

#### AWSの操作方法
- **マネジメントコンソール**: ブラウザから操作
- **AWS CLI**: コマンドラインから操作
- **Terraform**: IaC（Infrastructure as Code）ツール
- **SDK**: プログラムからAWSを操作

#### CORS
Cross-Origin Resource Sharing
ブラウザの同一オリジンポリシーを安全に緩和する仕組みです。
異なるドメイン間の通信を許可できます。

#### IAM
AWSの認証認可サービスです。

- **IAM Policy**: どのリソースへどの操作を許可するか定義します。
- **IAM User**: 人間向けのAWSアカウントです。
- **Access Key**: プログラムからAWSへアクセスするための認証情報です。
  - Access Key ID
  - Secret Access Key
  漏洩すると重大なセキュリティ事故につながります。
- **OpenID Connect（OIDC）**: アクセスキーを利用せず認証連携する仕組みです。GitHub Actionsとの連携でよく利用されます。
- **IAM Role**: AWSサービスやアプリケーションへ権限を付与する仕組みです。

- Webサーバー

### DevOps
Development（開発）とOperations（運用）が協力してサービス価値を継続的に向上させる考え方です。

#### なぜ必要か
- 顧客ニーズ変化への対応
- 高速なリリース
- 品質向上

#### ウォーターフォール開発
工程を順番に進める開発手法
メリット
- 管理しやすい
- 文書化しやすい
- 初学者も参加しやすい
デメリット
- 手戻りが大きい
- リリースまで時間がかかる

#### アジャイル開発
短期間で開発と改善を繰り返す手法
メリット
- 変化に強い
- 顧客要望を反映しやすい
デメリット
- 継続的なコミュニケーションが必要
- メンバーに一定のスキルが求められる

### Organization
GitHub上で組織管理を行う単位です。

#### Team
Organization内のメンバーグループです。
権限例
- Maintainer
- Member

#### Project
タスク管理機能
管理対象
- Issue
- Draft Issue
- Pull Request

#### カスタムフィールド
タスクに独自情報を追加できます。
種類
- テキスト
- 数値
- 日付
- 単一選択
- イテレーション

#### Projectビュー
- **テーブル表示**: スプレッドシート形式
- **ボード表示**: カンバン形式

#### フィルター
- **基本形式**: `FIELD:VALUE`
- **OR条件**: `label:bug,label:feature`
- **AND条件**: `status:open assignee:@me`
- **未設定**: `NO:assignee`

### リポジトリ公開範囲
- **Public**: 誰でも閲覧可能
- **Private**: 許可されたユーザーのみ
- **Internal**: Enterpriseメンバーのみ

### リポジトリ権限
- Read
- Triage
- Write
- Maintain
- Admin

### ブランチ戦略
- **Subversion（SVN）**: 中央集権型バージョン管理システム
- **Git**: 分散型バージョン管理システム。ブランチを利用して独立して開発できます。

#### 代表的なブランチ戦略
- **Git Flow**: 大規模開発向け
- **GitHub Flow**: シンプルな運用
- **GitLab Flow**: 環境管理を重視

### ブランチ保護
重要なブランチへの直接変更を防ぐ機能です。
設定例
- Pull Request必須
- レビュー必須
- コードオーナー承認必須
- ステータスチェック必須
- 特定ユーザーのみPush可能

#### コードオーナー
特定ファイルやディレクトリの責任者を定義する仕組みです。

#### ブランチ保護の確認
1. Featureブランチを作成
2. ファイルをコミット
3. Pull Requestを作成
4. レビュー依頼
5. 承認確認
6. マージ実施
